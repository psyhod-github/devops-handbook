# 03 · AWS CLI и EC2 — задания

## Уровень 1 — повторение главы

Пройдите практику главы целиком, только командами, без консоли:

1. Проверьте профиль: `aws sts get-caller-identity`.
2. Создайте Key Pair, Security Group (SSH только с вашего IP) и инстанс `t3.micro`.
3. Подключитесь по SSH.
4. Сделайте Stop → Start, сравните публичные IP до и после.
5. Удалите инстанс, Security Group и Key Pair.

!!! success "✅ Как проверить себя"
    - `aws sts get-caller-identity` → `Arn` заканчивается на `user/devops-course`.
    - До и после Stop/Start приватный IP одинаковый, публичный — разный.
    - После уборки `describe-instances` по тегу `lesson-ec2` → `terminated`, `lesson-sg` и `lesson-key` не находятся.

## Уровень 2 — мини-проект: скрипт «сервер одной командой»

Соберите команды главы в два скрипта: `up.sh` создаёт всё (ключ, SG, инстанс) и печатает команду для SSH, `down.sh` удаляет всё. На Windows можно писать `up.ps1` и `down.ps1` или использовать Git Bash.

**Требования:**

- Скрипт не содержит хардкода AMI ID и IP-адресов.
- `up.sh` печатает в конце готовую строку `ssh -i ... ec2-user@<IP>`.
- `down.sh` находит ресурсы по тегу и именам, а не по ID, запомненным вручную.
- Перед удалением `down.sh` показывает, что собирается удалить, и спрашивает подтверждение.

<details markdown="1">
<summary>💡 Подсказки</summary>

- Первая строка скрипта: `#!/usr/bin/env bash`, вторая: `set -euo pipefail` — остановиться на первой ошибке.
- Найти инстанс по тегу в `down.sh`:
  ```bash
  IDS=$(aws ec2 describe-instances \
    --filters "Name=tag:Name,Values=lesson-ec2" "Name=instance-state-name,Values=pending,running,stopped" \
    --query 'Reservations[].Instances[].InstanceId' --output text)
  ```
- Найти SG по имени: `--filters "Name=group-name,Values=lesson-sg" --query 'SecurityGroups[0].GroupId'`.
- Подтверждение: `read -p "Удалить $IDS? [y/N] " ans; [ "$ans" = "y" ] || exit 1`.
- Добавьте в начало обоих скриптов вывод `aws sts get-caller-identity --query Arn --output text`, чтобы видеть, в каком аккаунте вы работаете.
</details>

<details markdown="1">
<summary>✅ Критерии готовности</summary>

- [ ] `./up.sh` с нуля создаёт инстанс, на который можно зайти по SSH напечатанной командой.
- [ ] `./down.sh` после подтверждения удаляет всё; повторный запуск не падает, а сообщает, что удалять нечего.
- [ ] В скриптах нет строк вида `ami-0...`, `sg-0...`, `i-0...`, конкретных IP.
- [ ] Обратите внимание, сколько кода ушло на проверки «существует ли уже» и порядок удаления. Именно эту работу возьмёт на себя Terraform в главе 06.
</details>

## Уровень 3 — подумайте сами

<details markdown="1">
<summary>1. У вас два профиля: <code>devops-course</code> (учебный аккаунт) и <code>work</code> (рабочий). Как сделать так, чтобы случайно не удалить рабочие ресурсы учебным скриптом?</summary>

Несколько слоёв защиты:

- **Не делать рабочий профиль профилем `default`.** Тогда без явного указания профиля CLI просто не найдёт ключей.
- **Проверять аккаунт в скрипте:** сравнивать `aws sts get-caller-identity --query Account` с ожидаемым ID и выходить, если не совпадает.
- **Права:** у рабочего пользователя не должно быть прав на массовое удаление без необходимости (глава 04).
- **Разные аккаунты для разных окружений**, а не разные теги в одном аккаунте. Это стандартная практика AWS: ошибка в учебном аккаунте физически не может задеть продакшен.
</details>

<details markdown="1">
<summary>2. Вы запустили <code>run-instances</code> дважды по ошибке. Как найти и удалить лишний инстанс одной командой, не трогая первый?</summary>

У обоих одинаковый тег, отличаются время запуска и ID. Можно отсортировать по `LaunchTime` и взять последний:

```bash
aws ec2 describe-instances \
  --filters "Name=tag:Name,Values=lesson-ec2" "Name=instance-state-name,Values=running,pending" \
  --query 'sort_by(Reservations[].Instances[], &LaunchTime)[-1].InstanceId' --output text
```

И передать результат в `terminate-instances`. Мораль: императивные команды не защищают от повторного запуска (они не **идемпотентны**). Terraform, наоборот, сравнивает желаемое с существующим и повторно ресурс не создаст.
</details>

<details markdown="1">
<summary>3. Где на диске лежит ваш секретный ключ AWS и кто ещё на компьютере может его прочитать? Как уменьшить риск, если ноутбук украдут?</summary>

В `~/.aws/credentials` открытым текстом. Его может прочитать любой процесс, запущенный от вашего пользователя, включая вредоносные npm-пакеты и расширения.

Как снизить риск:

- шифрование диска (BitLocker, FileVault);
- минимальные права пользователя (глава 04): украденный ключ с правами только на EC2 опаснее не станет;
- **временные учётные данные** вместо постоянных: IAM Identity Center (`aws configure sso`) или роли (глава 05). Временный ключ истекает через часы;
- при подозрении на кражу — немедленно деактивировать ключ в IAM.
</details>
