# 02 · AWS: VPC и EC2 — задания

## Уровень 1 — повторение главы

Повторите практику главы с нуля, не подглядывая в шаги:

1. Создайте Key Pair, Security Group (SSH только с вашего IP) и инстанс `t3.micro` на Amazon Linux 2023.
2. Подключитесь по SSH и выполните `whoami`, `hostname`, `ip -4 addr show`, `curl -s https://checkip.amazonaws.com`.
3. Удалите всё созданное.

!!! success "✅ Как проверить себя"
    - `whoami` → `ec2-user`.
    - Приватный IP из `ip addr` начинается с `172.31.`, публичный из `checkip` совпадает с IP в консоли.
    - После уборки инстанс в статусе `Terminated`, учебных SG и Key Pair нет.

## Уровень 2 — мини-проект: веб-сервер руками

Превратите EC2 в веб-сервер со своей страницей. Запомните, сколько ручных шагов на это ушло: в главе 08 тот же результат получится автоматически.

**Что сделать:**

1. Запустите инстанс как в главе (Security Group уже пускает HTTP на порт 80).
2. На сервере установите nginx, запустите его и включите автозапуск.
3. Замените стандартную страницу своей: имя, дата, что угодно.
4. Откройте `http://<PUBLIC_IP>` в браузере.
5. Перезагрузите инстанс (**Instance state → Reboot**) и убедитесь, что сайт поднялся сам.
6. Удалите все ресурсы.

<details markdown="1">
<summary>💡 Подсказки</summary>

- Пакетный менеджер Amazon Linux 2023 — `dnf`: `sudo dnf install -y nginx`.
- Запуск и автозапуск одной командой: `sudo systemctl enable --now nginx`.
- Страница по умолчанию: `/usr/share/nginx/html/index.html`. Писать туда нужно с `sudo`, например:
  `echo "<h1>Hello from $(hostname)</h1>" | sudo tee /usr/share/nginx/html/index.html`.
- Сайт не открывается? Проверьте по цепочке: `systemctl status nginx` на сервере → `curl localhost` на сервере → правило HTTP в Security Group → в браузере именно `http://`, а не `https://`.
</details>

<details markdown="1">
<summary>✅ Критерии готовности</summary>

- [ ] `curl http://<PUBLIC_IP>` с вашего компьютера возвращает вашу страницу.
- [ ] После Reboot сайт снова доступен без ручных действий (`systemctl is-enabled nginx` → `enabled`).
- [ ] Вы записали список всех команд, которые выполнили. Он пригодится в главе 08.
- [ ] Все ресурсы удалены.
</details>

## Уровень 3 — подумайте сами

<details markdown="1">
<summary>1. Спроектируйте VPC для приложения: веб-сервер, доступный из интернета, и база данных, недоступная извне. Нужна устойчивость к отказу одной AZ. Какие подсети, CIDR и маршруты вы создадите?</summary>

Один из правильных вариантов:

| Подсеть | AZ | CIDR | Маршрут `0.0.0.0/0` |
|---------|----|------|---------------------|
| public-a | us-west-2a | `10.0.1.0/24` | → IGW |
| public-b | us-west-2b | `10.0.2.0/24` | → IGW |
| private-a | us-west-2a | `10.0.11.0/24` | → NAT (или маршрута нет) |
| private-b | us-west-2b | `10.0.12.0/24` | → NAT (или маршрута нет) |

VPC — `10.0.0.0/16`. Балансировщик нагрузки в публичных подсетях, веб-серверы и база — в приватных, в обеих AZ.

Security Groups:

- SG балансировщика: 80/443 от `0.0.0.0/0`;
- SG веб-серверов: 80 только от SG балансировщика;
- SG базы: порт базы только от SG веб-серверов.

Ключевая идея: в правилах SG источником может быть **другая Security Group**, а не только IP. Так связи между уровнями описываются по смыслу и не зависят от адресов.
</details>

<details markdown="1">
<summary>2. Утром SSH работал, а вечером из кафе — <code>Connection timed out</code>. Сервер не трогали. В чём дело и как это быстро проверить?</summary>

Сменился ваш публичный IP: в кафе другой провайдер. Правило SSH разрешает только утренний `/32`. Проверка: `curl https://checkip.amazonaws.com` и сравнить с источником правила в Security Group. Решение — изменить правило на новый **My IP**.

Если такое случается часто, есть подходы без открытого SSH вообще: **AWS Systems Manager Session Manager** (доступ через API AWS по IAM-правам, порт 22 закрыт для всех) или VPN.
</details>

<details markdown="1">
<summary>3. Сервер в приватной подсети без NAT Gateway. Сработает ли на нём <code>sudo dnf install nginx</code>? Как обойтись без NAT, который стоит $32 в месяц?</summary>

Нет: репозитории пакетов в интернете, а маршрута наружу нет. `dnf` будет ждать и упадёт по таймауту.

Варианты без NAT:

- **VPC Endpoints** — частный доступ к сервисам AWS (S3, ECR, SSM) без интернета. Для S3 есть бесплатный *gateway endpoint*, а репозитории Amazon Linux 2023 размещены в S3, поэтому `dnf` заработает.
- **Готовый образ**: собрать AMI или Docker-образ со всем нужным заранее, тогда на сервере ничего скачивать не нужно.
- Временно поместить сервер в публичную подсеть только на время настройки (плохая практика для продакшена).
</details>

<details markdown="1">
<summary>4. Инстанс остановили (Stop) и запустили (Start). SSH по старому IP не работает. Почему? Как сделать постоянный адрес?</summary>

Автоматический публичный IP выдаётся при старте и **освобождается при остановке**. После Start инстанс получает новый адрес. Приватный IP при этом сохраняется.

Постоянный публичный адрес — **Elastic IP**: его выделяют в аккаунт и привязывают к инстансу. Важно: Elastic IP тарифицируется как любой публичный IPv4, и **продолжает тарифицироваться, если его не освободить** после удаления инстанса. Частый скрытый расход у новичков.

В продакшене вместо этого обычно используют DNS-имя и балансировщик нагрузки, а не фиксированный IP сервера.
</details>
