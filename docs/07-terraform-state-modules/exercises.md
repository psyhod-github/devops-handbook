# 07 · Terraform: remote state и модули — задания

## Уровень 1 — повторение главы

1. Создайте бакет `tf-state-<account-id>` с versioning и политику `terraform-state-access`.
2. Перенесите state проекта в S3 через `terraform init -migrate-state`.
3. Удалите `.terraform/` и убедитесь, что после `init` план показывает `No changes`.
4. Получите `Error acquiring the state lock`, запустив `plan` во время ожидающего `apply`.
5. Вынесите ресурсы в модуль `modules/ec2` с блоками `moved` так, чтобы план показал `0 to add, 0 to destroy`.
6. Вызовите модуль второй раз и удалите всё через `terraform destroy`.

!!! success "✅ Как проверить себя"
    - `aws s3 ls s3://tf-state-<id>/tf-07/` показывает `terraform.tfstate`, а во время `apply` — ещё и `.tflock`.
    - Локального `terraform.tfstate` в папке нет.
    - После рефакторинга `terraform state list` показывает адреса `module.web.*`.
    - После `destroy` инстансов с тегом `Project=tf-lab` нет.

## Уровень 2 — мини-проект: dev и prod из одного модуля

Разложите проект по окружениям с отдельным state для каждого.

**Требования:**

```text
tf-07-envs/
├── modules/ec2/           ← модуль из главы (без изменений)
└── envs/
    ├── dev/               ← key = "tf-lab/dev/terraform.tfstate",  t3.micro
    └── prod/              ← key = "tf-lab/prod/terraform.tfstate", t3.small
```

- В каждой папке окружения — `versions.tf`, `backend.tf`, `main.tf`, `variables.tf`, `outputs.tf`.
- Модуль подключается через `source = "../../modules/ec2"`.
- Имена ресурсов содержат окружение (`tf-lab-dev`, `tf-lab-prod`).
- `terraform destroy` в `envs/dev` не трогает prod.

<details markdown="1">
<summary>💡 Подсказки</summary>

- `versions.tf` и `variables.tf` копируются в обе папки — это нормально, они маленькие. Повторяется только «обвязка», логика живёт в модуле.
- После создания обоих окружений `aws s3 ls s3://tf-state-<id>/tf-lab/ --recursive` покажет два разных файла state.
- В каждой папке свой `.terraform/` и свой `terraform.tfvars`.
- Альтернатива — **workspaces** (`terraform workspace new dev`) — один код и несколько state по префиксу `env:/`. Они удобны для одинаковых окружений, но легко ошибиться, в каком workspace вы сейчас. Многие команды предпочитают раздельные папки.
</details>

<details markdown="1">
<summary>✅ Критерии готовности</summary>

- [ ] В S3 два state: `tf-lab/dev/terraform.tfstate` и `tf-lab/prod/terraform.tfstate`.
- [ ] Инстансы `tf-lab-dev-web` (`t3.micro`) и `tf-lab-prod-web` (`t3.small`) работают одновременно.
- [ ] `terraform destroy` в `envs/dev` удаляет только dev; prod на месте.
- [ ] Всё удалено после проверки.
</details>

## Уровень 3 — подумайте сами

<details markdown="1">
<summary>1. Кто в команде должен иметь права на бакет со state, а кто нет? Чем опасен доступ на чтение state?</summary>

State содержит ID и атрибуты всех ресурсов, а часто и секреты: пароли баз данных, приватные ключи, токены — открытым текстом. Доступ на чтение state = доступ к этим секретам.

Хорошая практика:

- писать state может только тот, кто применяет изменения (CI-роль, узкий круг инженеров);
- читать — тоже узкий круг, а не «все разработчики»;
- для продакшена — отдельный аккаунт и бакет, шифрование ключом KMS (доступ к ключу ещё один слой контроля, все расшифровки видны в CloudTrail);
- секреты в Terraform по возможности не создавать вовсе, а передавать через Secrets Manager.
</details>

<details markdown="1">
<summary>2. Блокировка зависла: <code>Error acquiring the state lock</code>, а коллега говорит, что ничего не запускал. Ваши действия?</summary>

1. Посмотреть `Lock Info`: **кто** (`Who`), **когда** (`Created`), **какая операция**.
2. Связаться с этим человеком или проверить CI: не идёт ли там pipeline.
3. Если `Created` давно, а процесса точно нет (CI-агент упал, ноутбук выключили посреди apply) — `terraform force-unlock <ID>`.
4. Сразу после — `terraform plan`: упавший apply мог успеть создать часть ресурсов, и state может отличаться от реальности.

Никогда не снимайте блокировку «на всякий случай»: если apply действительно идёт, два процесса испортят state.
</details>

<details markdown="1">
<summary>3. Модуль используют 10 проектов. Вы хотите добавить в него обязательную переменную. Как не сломать всех сразу?</summary>

- Сделать переменную **необязательной** с безопасным `default`, чтобы старые вызовы продолжали работать.
- Хранить модули в отдельном репозитории и подключать по **тегу версии** (`?ref=v1.3.0`) или из приватного Registry с `version`. Тогда изменение модуля — это новая версия, а проекты переходят на неё по одному, через свой `plan`.
- Следовать semver: несовместимые изменения — новая мажорная версия (`v2.0.0`) и описание миграции.

Локальный `source = "./modules/..."` удобен для учёбы и одного проекта, но любое изменение модуля сразу влияет на все его вызовы.
</details>
